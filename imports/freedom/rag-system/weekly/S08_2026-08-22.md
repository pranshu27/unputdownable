## W4-3 - Metric Surfacing (Latency + Cost + Reliability)

Objective:
- Add measurable runtime telemetry for review questions and production readiness.

Deliverables:
1. Add request-level timing fields in /retrieve and /answer responses:
   - total_ms
   - retrieval_ms
   - rerank_ms (when enabled)
   - generation_ms (when llm=true)
2. Add response-level usage fields when available:
   - prompt_tokens
   - completion_tokens
   - total_tokens
   - estimated_cost_usd
3. Add local evaluation script/report for p50/p95 latency.

Acceptance Criteria:
- API responses include timing fields for both success and refusal cases.
- Token and estimated cost fields are populated when provider returns usage; null with reason when unavailable.
- A repeatable benchmark artifact is generated under eval/.

Concrete example output target:

## Worst-Case Planning (What Can Go Wrong and Mitigation)

1. Risk: telemetry changes break response contracts.
- Mitigation: add additive fields only; keep existing keys unchanged.

2. Risk: extra timing instrumentation adds overhead.
- Mitigation: use lightweight monotonic timers and avoid heavy logging in hot path.

3. Risk: token usage missing from provider response in some models.
- Mitigation: return null usage fields with usage_unavailable_reason.

4. Risk: relevance tuning reduces faithfulness.
- Mitigation: keep existing faithfulness gate active and compare before/after artifacts each run.

5. Risk: benchmark variance causes noisy decisions.
- Mitigation: run fixed dataset, fixed k, fixed mode, and at least 3 repeated passes before concluding.
